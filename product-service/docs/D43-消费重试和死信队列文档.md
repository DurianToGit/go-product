## 任务 1：写一份 D43 笔记

### 1. 什么是消费重试

消费失败后，不是立刻丢弃，而是再次尝试处理

### 2. 什么是死信队列

消息多次重试仍失败，就不能一直卡在主队列里，需要转移到“死信队列”中等待人工排查或补偿处理

### 3. 哪些错误适合重试

1. 需要数据持久化，且数据幂等
2. MySQL临时抖动
3. redis 网络抖动
4. 下游服务瞬时超时

### 4. 哪些错误不适合重试

1. 数据不存在
2. 消息字段缺失
3. JSON 格式错误
4. 代码逻辑本身写错

### 5. 为什么重试必须配合幂等

因为“重试”意味着同一条消息可能被处理多次，所以消费者一定要具备幂等能力

### 6. 在 go-product 中，库存扣减失败如何设计 retry / dlq

```
主 topic 消费失败
    ↓
进入 retry topic
    ↓
重试仍失败
    ↓
进入 dlq
```

## 任务 2：为 stock.deduct.requested 设计 retry / dlq 方案

1. 主 Topic：stock.deduct.requested
    * 作用：接收所有待处理的库存扣减请求，是库存扣减的原始输入队列。
    * 谁生产：order-service
    * 谁消费: stock-worker，库存服务中的主消费者，负责监听该Topic并执行实际的库存扣减逻辑。如果扣减成功，则流程结束；如果失败（如库存不足、数据库异常等），根据失败类型决定是否重试。
    * 消息里要不要带 retry_count：要，初始为0
2. 重试 Topic：stock.deduct.retry
    * 作用：存放需要重试的扣减请求。当主消费处理失败且允许重试时（如临时性异常），将消息转发至此Topic，等待后续再次消费。
    * 谁生产：stock-worker，库存服务的主消费者
    *
    谁消费：retry-stock-worker，库存服务中的重试消费者，专门监听stock.deduct.retry。消费逻辑与主消费者相同，执行库存扣减。若仍然失败，则继续判断是否重试，直到达到最大重试次数（如3次），然后转发至死信Topic。
    * 消息里要不要带 retry_count：要，与stock.deduct.requested的消息结构完全一致，但retry_count已递增
3. 死信 Topic：stock.deduct.dlq
    * 作用：死信队列，存储最终无法成功处理的扣减请求（如重试耗尽、业务校验永久失败等）。这些消息需要人工介入或后续补偿处理。
    * 谁生产：存服务的重试消费者（stock.deduct.retry的消费者），当某条消息重试次数达到上限且依然失败时，将其发送至此Topic。
    * 谁消费：一般由监控系统或人工处理平台消费，用于告警、记录日志、触发补偿流程等。通常不自动重新处理，而是留待管理员分析。
    * 消息里要不要带 retry_count：与原始消息一致，保留完整的业务字段和最终的retry_count，便于问题排查。

## 补充重试策略（延迟重试）
策略为延迟重试，做法如下

| 重试次数（失败后） | 延迟时间 | Topic                     |
| ------------------ | -------- | ------------------------- |
| 第 1 次失败        | 1 秒     | `stock.deduct.retry.1s`   |
| 第 2 次失败        | 5 秒     | `stock.deduct.retry.5s`   |
| 第 3 次失败        | 30 秒    | `stock.deduct.retry.30s`  |

**说明**：
- 每个 Topic 对应一个固定的延迟等级，生产者在决定重试时根据当前 `retry_count` 选择对应的 Topic。
- 消费逻辑统一，但可根据 Topic 判断当前处于第几次重试。
- 当消息在 `stock.deduct.retry.30s` 中消费失败后，不再继续重试，直接进入死信队列。

### 伪代码
```go
const (
    MaxRetry = 3
)

// 主消费者：监听 stock.deduct.requested
func consumeRequested(msg *Message) {
    err := deductStock(msg)
    if err == nil {
        // 成功，提交offset
        return
    }

    // 失败处理
    if msg.RetryCount >= MaxRetry-1 { // 已经是第3次失败（retry_count=2）
        sendToDLQ(msg)
        return
    }

    // 根据当前重试次数决定下一次延迟
    msg.RetryCount++
    var targetTopic string
    switch msg.RetryCount {
    case 1:
        targetTopic = "stock.deduct.retry.1s"
    case 2:
        targetTopic = "stock.deduct.retry.5s"
    case 3:
        targetTopic = "stock.deduct.retry.30s"
    }
    produceTo(targetTopic, msg, withDelay)
}

// 重试消费者：统一处理各延迟Topic
func consumeRetry(msg *Message, topic string) {
    err := deductStock(msg)
    if err == nil {
        return
    }

    // 根据当前retry_count判断是否达到最大重试
    if msg.RetryCount >= MaxRetry {
        sendToDLQ(msg)
        return
    }

    // 继续下一次重试（递增retry_count并选择对应延迟Topic）
    msg.RetryCount++
    var nextTopic string
    switch msg.RetryCount {
    case 1:
        nextTopic = "stock.deduct.retry.1s"
    case 2:
        nextTopic = "stock.deduct.retry.5s"
    case 3:
        nextTopic = "stock.deduct.retry.30s"
    }
    produceTo(nextTopic, msg, withDelay)
}
```
